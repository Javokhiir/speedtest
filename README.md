# speedtest

Консольный скрипт для замера скорости скачивания. Делает 10 запросов **последовательно** к указанному адресу, дожидается полного ответа на каждый, затем печатает среднее время запроса, общий объём скачанных данных и скорость.

Написан на Node.js без зависимостей: используется встроенный `fetch`.

## Запуск

Нужен Node.js 18 или новее. Устанавливать ничего не надо.

```bash
git clone https://github.com/Javokhiir/speedtest.git
cd speedtest
node speedtest.js https://proof.ovh.net/files/10Mb.dat
```

Адрес может быть любым `http`/`https` URL: тяжёлая картинка, архив, тестовый файл. В примере взят файл на 10 МБ, который OVH держит специально для замеров скорости. Лучше брать файл на несколько мегабайт: на маленьком время уходит на установку соединения, а не на скачивание.

Параметры:

| Флаг | По умолчанию | Что делает |
|------|--------------|------------|
| `--count N` | 10 | число запросов |
| `--parallel N` | 1 | сколько запросов идёт одновременно; 1 значит строго по очереди |
| `--timeout SEC` | 60 | таймаут одного запроса в секундах |
| `--help` | | показать справку |

```bash
node speedtest.js https://example.com/big-photo.jpg --count 3 --timeout 30
```

## Единицы измерения

- **Время запроса** в секундах (`s`): от отправки запроса до получения последнего байта тела.
- **TTFB** (time to first byte) в секундах: часть времени запроса до начала ответа сервера, то есть до прихода заголовков. Остальное время уходит на скачивание тела.
- **Объём** в мегабайтах (`MB`), **1 MB = 1 000 000 байт**.
- **Скорость** в **мегабитах в секунду (`Mbit/s`)**, как в тарифах провайдеров. В скобках то же значение в мегабайтах в секунду (`MB/s`), 1 MB/s = 8 Mbit/s.

Формула: `скорость = сумма байт × 8 / 1 000 000 / сумма времени всех запросов`.

Скорость считается по общим суммам, а не как среднее скоростей отдельных запросов. Так каждый запрос учитывается пропорционально своему объёму и времени.

Строка `Speed without TTFB` показывает ту же скорость без ожидания ответа сервера: `сумма байт / (сумма времени − сумма TTFB)`. Если она заметно выше основной, время теряется на ответе сервера, а не на канале.

## Параллельный режим

По умолчанию запросы идут по очереди, как в задании. Флаг `--parallel N` запускает N запросов одновременно. Один поток часто не загружает канал полностью, поэтому параллельный замер ближе к его реальному максимуму.

```bash
node speedtest.js https://proof.ovh.net/files/10Mb.dat --parallel 5 --timeout 180
```

В этом прогоне пять потоков дали 13,12 Mbit/s против 8,66 Mbit/s в одном потоке на том же файле.

В этом режиме скорость считается иначе: `сумма байт / общее время прогона` (`Wall-clock time`). Складывать время запросов здесь нельзя: они идут одновременно, сумма получится в несколько раз больше реального времени, а скорость во столько же раз меньше. Скорость в строке каждого запроса показывает только его долю канала.

## Как это работает

- Запросы выполняют «воркеры»: каждый берёт следующий номер запроса только после завершения своего предыдущего. При `--parallel 1` воркер один, поэтому запросы идут строго по очереди.
- `fetch` возвращает ответ, как только пришли заголовки. В этот момент фиксируется TTFB, затем тело читается потоком, по кускам. Байты считаются по мере прихода, файл не хранится в памяти, поэтому размер файла не ограничен.
- Отправляются заголовки `Accept-Encoding: identity` и `Cache-Control: no-cache`, чтобы мерить реальные байты файла, а не сжатую или закешированную копию.
- Неудачный запрос (таймаут, сетевая ошибка, HTTP-статус не 2xx) печатается в логе и не входит в итоги; замер при этом продолжается.

Коды выхода: `0` если все запросы успешны, `2` если часть запросов не удалась, `1` если не удался ни один или аргументы неверны.

## Что стоит учитывать

- Первый запрос обычно медленнее остальных: в его TTFB входят DNS, TCP и TLS. Следующие запросы переиспользуют то же соединение (keep-alive).
- Замер идёт до одного сервера. Это скорость скачивания с этого сервера, а не гарантированный максимум канала: результат зависит от самого сервера и маршрута до него.
- В параллельном режиме в общее время прогона входит и время неудачных запросов. Каждый запрос при этом идёт медленнее, потому что канал делится между потоками, так что для больших файлов стоит поднять `--timeout`.
- Некоторые серверы ограничивают частые запросы и отвечают `HTTP 429`. Например, Wikimedia начала так отвечать после нескольких прогонов подряд. Такие запросы попадают в лог как неудачные.

## Тесты

```bash
npm test
```

Тесты написаны на встроенном `node:test` и поднимают локальный HTTP-сервер, интернет для них не нужен. Проверяется точный подсчёт байт, разделение TTFB и времени тела, последовательность запросов (по умолчанию никогда не больше одного одновременно), параллельный режим, обработка HTTP-ошибок и таймаута, расчёт итогов в обоих режимах и разбор аргументов.
